# 性能规范与基准

## 目的

本文档规定 LAN Chat 的高性能数据路径、资源上限、调度参数、基准环境、验收计算和不达标排查顺序。性能参数是 V1 的实现约束，不得由各平台自行选择不同默认值。

## 前置知识

- 已阅读 [总体架构](02-architecture.md) 的 TCP 数据连接和文件句柄边界。
- 已阅读 [网络协议](03-network-protocol.md) 的 `data_entry` 连续字节格式。
- 能使用 `iperf3`、系统资源监视器和 OpenSSH SFTP。

## 性能目标

| 场景 | 硬性目标 |
|---|---|
| 1GbE、两端 SSD、单个 10GB+ 文件 | 中位有效吞吐 105-115 MB/s |
| Wi-Fi、两端本地闪存/SSD | 达到同方向 `iperf3` 吞吐的至少 85% |
| 与 SFTP 对比 | 同设备、同网络、同源/目标目录下，中位吞吐不得低于 SFTP |
| 100GB 文件 | Rust 核心与传输新增常驻内存不超过 128MiB |
| UI 进度 | 每个任务最多 4 次/秒，不影响数据通道 |
| 崩溃恢复点 | 每经过 1 秒或 64MiB（任一先到）最多提交一次 |
| 完成延迟 | 最后一字节到达后 2 秒内进入 completed，受存储 flush 限制时记录原因 |

“有效吞吐”计算为最终成功保存的文件字节数除以从第一字节发送到最终文件发布成功的时间。不得只报告 Socket 写入速度。

## 数据路径

```text
发送：OS 文件句柄 -> Rust 复用缓冲区/零拷贝 -> TCP data socket
接收：TCP data socket -> Rust 复用缓冲区 -> OS 文件句柄 -> flush -> 最终发布
```

以下路径禁止出现：

```text
文件字节 -> Dart Uint8List
文件字节 -> JSON/Base64
文件字节 -> SQLite BLOB
每个缓冲块 -> FFI 回调
每个缓冲块 -> 回执或数据库事务
```

## 不可违反的性能规则

1. 文件字节只在 Rust 和操作系统句柄之间流动。
2. 单个大文件使用一个 TCP 数据流；局域网低延迟下不为单文件拆多连接。
3. 不计算默认文件哈希，不压缩，不扫描内容，不在传输中生成缩略图。
4. 文件夹在同一数据连接中按清单顺序连续发送，不为每个小文件重新握手。
5. 进度在内存累计，按 250ms 节流发 UI；UI 不轮询数据库。
6. 续传点按“1 秒或 64MiB先到”写数据库，不按缓冲块写；中间续传点不得调用 `fsync`/`sync_data` 阻塞数据循环。
7. 数据连接读写循环不得持有 SQLite、UI 事件队列或群状态锁。
8. 最终 flush 和发布完成后才报告 completed。

## 缓冲区

### 默认值

- 数据连接用户态读缓冲：1MiB。
- 数据连接用户态写缓冲：1MiB。
- 控制连接帧头缓冲：4KiB 起步，按实际 JSON 长度精确扩容，上限遵循协议。
- 每个活动数据连接最多持有两个 1MiB 数据缓冲，一个用于读取、一个用于写入/调度。
- 缓冲通过池复用；任务完成后归还，不反复分配大型 Vec。

### 调整规则

- 64KiB、256KiB、1MiB、4MiB 只在性能基准中比较，默认从 1MiB 开始。
- 若 1MiB 已达到网络上限 95% 以上，不为追求微小提升增加到 4MiB。
- Android DocumentsProvider 若单次大 I/O 明显退化，可以只在 Android 适配层降到 256KiB，必须用基准证明。
- 任何平台的总缓冲预算都计入 128MiB 内存门槛。

## Socket 配置

### 控制连接

- 开启 `TCP_NODELAY`，降低小 JSON 消息延迟。
- 开启 TCP keepalive；应用层仍按协议发送 ping/pong。
- 写入必须通过单一有界队列。

### 数据连接

- 不需要 `TCP_NODELAY`；数据为连续大写入。
- 先使用操作系统 TCP 自动调优。
- Windows 和 Android V1 不覆盖 `SO_SNDBUF`/`SO_RCVBUF`；真机 A/B 已证明手工 4MiB 会降低吞吐。未来平台若要覆盖，必须先用同一设备 A/B 证明更快。
- 不设置极小超时；30 秒无字节进展由应用层判断。
- Windows 大文件发送在普通缓冲实现通过后再试验零拷贝；零拷贝失败必须自动回退，不改变协议。

## 文件 I/O

### 发送端

- 打开后立即读取实际 size/mtime 并与清单比较。
- 发送完原始字节、发出 data_end 前再次检查 size/mtime；变化时终止并让接收端保留未发布 partial。
- 顺序读取，不做随机预读。
- Windows 可以提示系统顺序扫描访问模式。
- Android 直接从 SAF FD 读取；不得先复制到应用缓存。
- 续传只 seek 到对端确认 offset 后继续。

### 接收端

- 尝试预分配最终大小；文件系统/Provider 不支持时继续顺序写，不将预分配失败视为传输失败。
- partial 与 final 位于同一目标目录。
- 只维护连续前缀，不维护稀疏块位图。
- 每次持久化 offset 前，保证数据库记录不超过已经成功写入文件句柄的连续字节；进程重启时再用 partial 实际长度下调数据库 offset。
- 中间续传点只 `flush` 用户态缓冲并提交 offset，不强制设备落盘；最终发布前执行一次 `sync_data`/等价平台提交。这样保证应用进程被杀可恢复，同时避免每 64MiB 阻塞整个 TCP 数据循环。
- 最后 flush、校验文件大小并发布；默认不做全文件二次读取。

## 调度策略

固定上限：

- 全局活动数据连接最多 4 条。
- 同一对端最多 2 条。
- 同一 transfer 最多 1 条。
- 同一文件夹 transfer 内按 entry 顺序，不并行读取多个小文件。

调度优先级：

1. 用户刚刚点击“继续”或“重试”的任务。
2. 已经传输超过 0 字节的恢复任务。
3. 新任务按创建时间 FIFO。

公平规则：连续发送 1GiB 后允许同优先级其他 peer 获得一个调度槽，但不切断当前单文件连接；公平性主要通过 4 个全局槽和每 peer 2 个槽实现。

不要基于文件扩展名、聊天是否置顶或设备平台改变优先级。

## SQLite 和事件开销

### 续传点

每个活动 transfer 维护：

```text
last_persisted_at
bytes_since_persist
current_offsets
```

当 `elapsed >= 1s OR bytes_since_persist >= 64MiB` 时，把所有当前 entry offset 在一个事务中提交。若数据库线程忙，合并为最新快照，不排队多个旧进度写入。

### UI 进度

- 速度使用最近 2 秒滑动窗口，不用“总字节/总时间”显示瞬时速度。
- 250ms 发布一次最新值；该窗口内多次更新覆盖旧值。
- ETA 仅在连续 2 秒有非零速度且剩余大于 0 时显示。
- 速度为 0 超过 3 秒显示“正在重新连接”，不显示无限大 ETA。

### 日志

- 数据循环不逐 read/write 记录日志。
- 每 10 秒最多记录一次活动任务摘要，仅 debug 级别。
- 完成日志一条包含总量、耗时、平均速度、峰值内存、续传次数和数据库提交次数。

## 小文件优化

文件夹中的小文件常受元数据和平台调用限制，采用：

- 一次 Offer 发送完整 file/directory 清单，空目录只产生元数据和平台创建操作，不进入数据流。
- 一条数据连接连续发送多个 entry。
- Windows 在 Rust 内直接复用目录与文件句柄打开逻辑。
- Android 每个 entry 仍需平台打开 FD；平台请求按清单顺序预取下一个 FD，但同时预开最多 4 个，防止句柄耗尽。
- 缩略图和媒体索引在全部数据保存后异步处理。

V1 不把小文件打包成自定义归档，因为用户应在接收目录得到原目录结构，且归档会引入第二次复制和恢复复杂度。

## 内存预算

100GB 单任务测试时新增内存预算：

| 项目 | 上限 |
|---|---:|
| 四条活动连接缓冲 | 16MiB |
| 协议与文件清单 | 32MiB |
| 任务、队列与事件 | 16MiB |
| SQLite page/cache 增量 | 16MiB |
| 平台与 FFI 临时对象 | 16MiB |
| 余量 | 32MiB |
| 总计 | 128MiB |

单个 10,000 条文件清单解析不得复制成三套长期对象。Rust 领域模型持有一份，Flutter 只分页获取显示项。

## 标准基准环境

### 硬件与网络记录

每次结果必须记录：

- 两端设备型号、CPU、内存。
- 源盘和目标盘类型及可用空间。
- 操作系统版本、LAN Chat 构建号。
- 有线链路速率，或 Wi-Fi 标准、频段、信号和协商速率。
- 是否经交换机、路由器或 USB 网卡。
- 文件系统/Android DocumentsProvider 名称。

### 测试文件

- 大文件：至少 10GiB 的不可压缩内容；最终验收再用 100GiB。
- 中型集合：1,000 个 1MiB 文件。
- 小文件集合：10,000 个 4-64KiB 文件，总量至少 256MiB。
- 文件生成一次后供 LAN Chat 和 SFTP 使用，不在不同目录重新生成不同内容。

### 测量顺序

1. 重启两端测试应用，停止云盘、杀毒全盘扫描和其他大流量任务。
2. 运行同方向 `iperf3` 30 秒，记录接收端吞吐；Wi-Fi 再反方向运行一次。
3. 使用系统 OpenSSH SFTP 把相同测试文件从相同源盘传到相同目标盘。
4. 删除目标文件并等待 30 秒，使写回稳定。
5. 使用 LAN Chat 传相同文件到同一目标目录。
6. 每种方式执行一次预热和三次计分，取三次中位数。
7. 交换发送/接收方向重复。

不得选择性只报告最好一次，也不得拿 `iperf3` 比特率直接与 MB/s 混用。换算：`MB/s = Mbit/s / 8`，报告时注明十进制或二进制单位。

## SFTP 对照

- 使用相同两台设备和相同网络方向。
- 使用默认安全的 OpenSSH SFTP，不关闭其加密。
- 源和目标目录与 LAN Chat 一致。
- 计时包含文件传输但不包含用户输入密码时间。
- 若 SFTP 因 CPU 加密成为瓶颈，仍以其实际中位速度为产品下限；LAN Chat 还必须满足 Wi-Fi 85% 或 1GbE 105MB/s 的独立目标。

## 性能门禁

每个里程碑执行不同门禁：

- P0 Rust CLI 样机：大文件达到 `iperf3` 的 90%，证明数据通道设计。
- P1 接入 SQLite/续传：相对 P0 降幅不超过 3%。
- P2 接入 Flutter 进度：相对 P1 降幅不超过 3%。
- P3 Windows/Android 真机：满足最终吞吐、内存和 SFTP 门槛。
- 发布候选：三次中位达标，且没有一次低于门槛 90%。

性能门禁失败时不得继续用“以后优化”关闭任务。

## 不达标排查顺序

1. **先测网络上限**：`iperf3` 本身是否达标，Wi-Fi 是否受信号和路由器限制。
2. **再测磁盘上限**：本地顺序读写同一测试文件，确认源盘和目标盘不慢于网络。
3. **检查数据路径**：确认没有 Dart、Base64、哈希、压缩、缩略图或逐块日志。
4. **分析 CPU**：Rust 是否单核满载，是否发生大量 JSON/FFI 调用。
5. **分析系统调用**：read/write 大小是否接近 1MiB，是否出现大量小写入。
6. **检查数据库**：续传点是否误写成每缓冲一次，WAL 是否异常增长。
7. **检查 Socket**：是否重传、窗口过小、连接频繁建立或被防火墙检查。
8. **检查 Android Provider**：直接本地存储 Provider 与第三方云 Provider 对比。
9. **最后调参数**：只在有 profiler 证据时调整缓冲、并发或 Socket 选项。

## 示例：1GbE 结果判定

```text
iperf3:       941 Mbit/s = 117.6 MB/s
SFTP median:  96.2 MB/s
LAN Chat:    109.4 MB/s
```

结果通过，因为 LAN Chat 位于 105-115MB/s 目标内，高于 SFTP，且达到 `iperf3` 字节吞吐的 93%。

若 LAN Chat 为 101MB/s，即使高于 SFTP 也未达到 1GbE 独立门槛，仍判失败。

## 2026-08-27 Windows 到 Android 实测

本节是 Rust 数据通道样机证据，不替代正式 App + Android SAF 的 P3 发布验收。

环境：

- 发送端：Windows 11 Pro 10.0.26200，Ryzen 9 9950X3D，96GiB 内存，2.5GbE 接入局域网。
- 接收端：Xiaomi M2012K11G，Android 14/API 34，约 7.1GiB 内存，Wi-Fi 6、5GHz、RSSI -47dBm、协商速率 2401Mbps。
- 方向：PC `10.1.1.203` 到 Android `10.1.1.161`。
- SFTP：Termux OpenSSH 10.5p1 默认加密，目标目录与 LAN 样机相同。
- LAN 样机：1MiB 用户态缓冲、单 TCP 流、最终 `sync_all` 后 ACK；文件字节不经过 Flutter。
- 手机在全部计分轮和 100GiB 压力测试中保持 `Dozing`。

10GiB 预热与三次计分，单位均为十进制 MB/s：

| 阶段 | iperf3 PC -> Android | SFTP | LAN 数据通道 |
|---|---:|---:|---:|
| 预热 | 约 211.8 | 143.60 | 190.66 |
| 第 1 轮 | 206.49 | 119.72 | 210.91 |
| 第 2 轮 | 176.16 | 108.88 | 212.20 |
| 第 3 轮 | 175.04 | 100.82 | 209.59 |
| 三轮中位数 | 176.16 | 108.88 | 210.91 |

Wi-Fi 在每轮 `iperf3` 与稍后的文件传输之间有明显波动，因此不把中位数相除解释为精确链路利用率。可确定的结论是：LAN 数据通道三轮中位数高于 SFTP `93.7%`，且每轮均高于该轮前置 `iperf3` 结果的 `85%` 门槛。

100GiB 流式压力结果：

| 字段 | 结果 |
|---|---:|
| 实际通过 TCP 并写入的字节 | 107,374,182,400 |
| 总耗时 | 510.15s |
| 有效吞吐 | 210.47MB/s |
| 接收进程峰值内存 | 4,755,456 bytes（4.54MiB） |
| 发送进程峰值内存 | 10,575,872 bytes（10.09MiB） |
| 最终同步 | 1.31s |
| 最终文件大小 | 107,374,182,400 bytes |

该轮使用 100GiB 稀疏源文件，但网络与目标盘实际处理了全部逻辑字节；它证明吞吐和内存不会随文件大小增长。按 [测试计划](08-test-plan.md#异常情况)，稀疏源不能签署最终 `PERF-007` 内容正确性，正式发布前仍需用非稀疏源文件执行全内容校验。

本轮 A/B 定位还确认：无条件设置 4MiB `SO_SNDBUF`/`SO_RCVBUF` 会把 1GiB 吞吐压低到约 125.2MB/s；恢复操作系统 TCP 自动调优后，同条件达到约 190.8MB/s。因此正式核心不再覆盖数据 Socket 缓冲大小。

### 正式 App + 系统 SAF 验收

同日又使用 Windows Debug 正式 Rust/TCP 发送路径和 Android 系统 `ExternalStorageProvider` Tree（`DCIM/Camera`）完成两轮接收，文件字节未经过 Flutter。手机全程锁屏，Android 前台服务、UDP/TCP 和 SAF 写入持续运行。

| 文件 | 结果 |
|---|---:|
| 10GiB 非稀疏文件 | `10,737,418,240` bytes，约 `49.8s`，Windows 工作集峰值增量约 `14.8MiB` |
| 100GiB 非稀疏文件 | `107,374,182,400` bytes，`576.6s`，`186.22 MB/s` |
| 100GiB Windows 工作集峰值增量 | `34.57MiB` |
| 100GiB Android PSS 峰值增量 | `1.34MiB` |

100GiB 任务 `01a042ba-6b1b-7c90-9048-12d02bf71dd8` 在两端均为 `completed`，双方 `persistedBytes` 均为 `107374182400`。接收端先写 `.partial`，完成后原子改名，最终无 partial 残留。Windows 非稀疏源文件与 Android SAF 最终文件的 SHA-256 均为 `f0b14a8da7f1c48a0846647a078b97956edd8df451a62fc4b466879aa24d4fd7`。该轮正式签署 `PERF-007` 的容量、流式内存、真实 SAF 和全内容一致性要求。

10GiB 任务 `01a042b3-1944-7dc3-b456-316de226c14c` 的源/目标 SHA-256 均为 `732377e7f4a2abdc13ddfa1eb4c9c497fd2a2b294674d056cf51581b47dd586d`，用于在 100GiB 前确认真实 SAF Tree 的创建、写入和原子改名链路。

### SQLite 与 Flutter 进度分阶段 A/B

为隔离控制面建立等待，`PERF-002` 只计任务首次进入 `transferring` 到双方 `completed` 的数据阶段。P0 使用同一 10GiB Windows 源文件和 Android 普通文件目标的 `perf_harness`；P1 使用正式 Rust 数据路径、SQLite WAL 和 1 秒/64MiB 续传点，但由 Debug-only 开关丢弃 Flutter 的进度 UI 消费。两组均在手机锁屏时执行。

| 阶段 | 三轮十进制 MB/s | 中位 | 相对前级 |
|---|---|---:|---:|
| P0 Raw TCP（相邻无线时段） | `189.134 / 185.403 / 190.704` | `189.134` | - |
| P1 SQLite/续传 | `152.166 / 190.276 / 191.998` | `190.276` | `+0.60%` |

P1 第一轮遇到明显无线降速，但三轮全部完成且字节数准确；紧接 P1 执行的 P0 三轮把同一时段网络上限定位在约 185-191MB/s，不能拿更早 212MB/s 的无线时段作为分母。按三轮中位，SQLite/续传没有造成吞吐下降，`PERF-002` 通过。

`PERF-003` 使用相邻时段、相同源/目标和相同端到端计时，仅切换 Flutter 是否消费每 250ms 的进度事件：

| Flutter 进度 | 三轮十进制 MB/s | 中位 | 相对 P1 |
|---|---|---:|---:|
| 关闭 | `180.658 / 192.952 / 196.513` | `192.952` | - |
| 开启 | `195.436 / 195.240 / 188.074` | `195.240` | `+1.19%` |

Flutter 进度开启后没有下降，`PERF-003` 通过。Debug 服务扩展只在断言开启的构建中注册；Release 始终消费正常进度事件，不存在用户可关闭的性能模式。

## 2026-08-27 Android 到 Windows 实测

本节使用正式 Android Debug 应用的 Rust/TCP 文件发送路径和 Windows 默认接收路径，不使用 `perf_harness`。手机在三轮 LAN Chat 和三轮 SFTP 中均保持锁屏，源文件始终是应用私有目录中的同一份 10GiB 非稀疏文件。

环境：

- 发送端：Xiaomi M2012K11G，Android 14/API 34，Wi-Fi 6、5GHz。
- 接收端：Windows 11 PC `10.1.1.203`；LAN Chat 写入 `Downloads/LAN Chat`。
- SFTP 客户端：Android instrumentation 中的 Apache MINA SSHD 2.15.0，1MiB 应用缓冲。

## 异常情况

- Android 目标是云盘 Provider：不纳入局域网满速验收，UI 提示选择本地存储；功能正确性仍需测试。
- Wi-Fi `iperf3` 波动超过 15%：改善测试环境后重测，不用最低一次作为网络上限。
- 目标盘空间不足导致末尾失败：该次不计性能成绩，计入故障测试。
- 系统缓存使 SFTP 或 LAN Chat 读取异常快：两者使用同一预热顺序，并报告缓存状态。
- 小文件无法达到大文件吞吐：使用每秒文件数和总完成时间单独比较，仍要求不慢于 SFTP。
- flush 超过 2 秒：记录“数据已接收，正在保存”，完成计时仍包含 flush。
